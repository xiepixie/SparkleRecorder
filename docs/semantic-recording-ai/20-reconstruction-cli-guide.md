# Macro Reconstruction CLI Guide

Updated: 2026-09-06
Status: Implemented strict authoring Interface; live acceptance pending

Use `SparkleRecorder reconstruction` to prepare a local evidence package, inspect candidate action IDs, and import a complete candidate. The implementation lives in `MacroReconstructionCLI.swift` and `MacroReconstructionPackage.swift`; this guide does not establish a passing build or installed-app acceptance. The active ledger is [19-reconstruction-product-implementation-plan.md](19-reconstruction-product-implementation-plan.md).

## Export a source package

Find the saved macro UUID through the existing `SparkleRecorder workflow macros --json` catalog, then run:

```sh
SparkleRecorder reconstruction export --macro-id <UUID> --output /absolute/path/reconstruction-package --json
```

The output directory must not already exist. Omitting `--output` creates a uniquely named `reconstruction-<macro UUID>-<UUID>` directory beneath the current directory. Export reads a complete accepted repository snapshot. If the macro links a semantic recording, that bundle must load so the package builder can evaluate privacy policy.

Visual bytes require explicit inclusion:

```sh
SparkleRecorder reconstruction export --macro-id <UUID> --output /absolute/path/reconstruction-with-video --include-video --json
```

`--include-video` requests permitted video and frames, together with available persisted observations. It does not upload anything or invoke a model. Missing artifacts produce warnings. Suppressed video is withheld unless verified full-file clock evidence supports the renderer's timing and the redaction receipt covers the required suppression ranges with a distinct artifact. Suppressed frames likewise require matching source and mask coverage. Missing clock provenance is reported; stream PTS alone does not prove movie/session alignment.

The current package is `macro-reconstruction-package/v4`. Its fixed files are `harness.json`, `authoring-contract.json`, `source-context.json`, `reconstruction.json`, `candidate-template.json`, and `manifest.json`; `candidate.json` is the only external-author output. `harness.json` is intentionally small and supplies the version ledger, file ownership and staged reading plan. `authoring-contract.json` owns the complete executable vocabulary, enum names, validator-facing rules and faithful/robust policy. `source-context.json` v3 is a lightweight Macro/Playback-Surface overview and deliberately excludes raw events; `candidate-template.json` is the single exported raw-event baseline and strict output shape. `reconstruction.json` v3 is the primary action inventory. `alignment.json` is present only when current source-event identity is verified. When aligned visual bytes are explicitly included, `visual-inspection.json` gives action-linked video seek ranges, exported key-image candidates, measured frame points, bounded OCR/AX observation summaries, and primary/context crop regions. The summary records a total observation count even when only the nearest bounded subset is embedded. There is no separate reconstruction-package `observations.json` dump. Explicitly included artifacts and their SHA-256 values appear in `manifest.json`. SparkleRecorder does not provide an AI screenshot tool; an external AI may use its own permitted video/image tools to seek, screenshot, crop, and zoom evidence. Package generation still rejects source fields that need known privacy sanitization. The actual movie container remains MOV or MP4 according to its artifact rather than renaming MOV bytes.

## Author and inspect the complete candidate

Give the external author only the package/evidence you intend to share. Start with `harness.json` and follow its staged reading plan: understand the Macro from `source-context.json` + `reconstruction.json` + `manifest.json`; inspect optional evidence only for fragile/ambiguous actions; load `authoring-contract.json` + `candidate-template.json` only when drafting and self-checking the complete Candidate. Preserve `sourceRevision`. Surface identity remains App-owned: the candidate refers to existing Playback Surfaces only through `event.surfaceId`. This CLI performs no model invocation and cannot certify which evidence an external author viewed.

After authoring, the AI tool should write the complete result to `candidate.json` inside the exported reconstruction package. You may also keep a standalone `candidate.json`. The file must follow the same strict candidate authoring Interface as `candidate-template.json`; a full Library `SavedMacro` is not accepted as an external candidate document. List candidate action IDs with:

```sh
SparkleRecorder reconstruction inspect --macro /absolute/path/candidate.json --json
```

A positional file path is also accepted. Inspection uses the same strict candidate decoder as import and `MacroActionReconstructor` with literal revision `candidate`. The returned action IDs belong in coverage targets; source IDs come from exported `reconstruction.json`. Inspection lists structural action identity; importing performs source-aware normalization and coverage validation. Any Library/runtime-owned macro field in external candidate JSON is rejected rather than silently ignored.

Supported playback capabilities are the existing raw mouse/keyboard/scroll events and text locators, `waitForText`, and `verifyText`. No image, pixel, region-change, or stability event is added. `authoring-contract.json` embeds `macro-candidate/v4`, the authoritative macro/event/anchor field allowlists, decoder-required event fields, numeric limits, every `RecordedEvent.Kind` code plus its enum name/meaning, every `ActionGroupKind` plus its executable representation, the accepted string enums (`coordinateBinding`, `coordinateStrategy`, `locatorFallbackPolicy`, `matchMode`, coverage dispositions), and validator-facing authoring rules. Current limits include 100,000 events, a nondecreasing 24-hour timeline, explicit positive text deadlines up to 3,600 seconds, coordinate magnitude at most 1,000,000 and normalized coordinates in `[0, 1]`. Text verification remains a single observation. Source Revision Playback Surfaces are described in `source-context.json` and colocated with actions in `reconstruction.json`; candidate JSON deliberately omits `macro.surfaces` and chooses among existing surfaces only through explicit `event.surfaceId`. Only the App's Candidate Editor may rebind a live target window. Every text-backed mouse action, `waitForText`, and `verifyText` requires an explicit surface. Locator-backed mouse input also requires target-window binding and locator-only strategy, and a mouse-down/up gesture keeps the same surface, Text Anchor, fallback policy, and timeout throughout. The robust/faithful policy is nested in `authoring-contract.json`; robust mode prefers content-normalized `TextAnchor` geometry when aligned evidence supports it. Playback resolves those regions against that Playback Surface's current content frame, so window movement and resizing do not require rewriting the candidate and multi-window macros never guess an arbitrary first surface.

`reconstruction.json` is a versioned `macro-reconstruction-action-context/v3` document. It carries action-level AI context directly: `surfaceID`, source/global points, available content-normalized points, text semantics, and a read-only surface description are colocated with each Reconstruction Action. It also includes compact deterministic semantics such as pointer button/click count, physical-key labels such as `⌘W` / `⌥2` / `Return`, bounded text-input previews, and aggregate scroll deltas. These summaries are deliberately small so the AI can triage most actions without opening the raw event template; path-sensitive details still come from raw/mechanical evidence on demand.

Coverage includes every source action, including inferred fixed waits. Transformations reference actual candidate action IDs and provide reasons; noise removal has no replacement target. `unresolved` coverage and known `uncertainActionIDs` remain visible for review and can be tested, but acceptance requires explicit acknowledgement or correction. Input balance is checked over enabled events. Normalization preserves source identity, personalization, links, statistics, loops, speed, window-follow policy, chaining, and Source Revision Playback Surfaces for external authoring, then replaces candidate events and refreshes caches. App-owned Candidate Draft window rebinding is retained separately and requires a fresh test.

## Import for review and testing

```sh
SparkleRecorder reconstruction import --macro-id <UUID> --candidate /absolute/path/reconstruction-package --json
```

`--candidate` accepts either the exported reconstruction package directory or a standalone `candidate.json`. Current v4 package-directory import is provenance-aware: SparkleRecorder requires `harness.json`, `authoring-contract.json`, `manifest.json`, `source-context.json`, `reconstruction.json`, `candidate-template.json`, and the AI-authored `candidate.json`; verifies the canonical Harness/index, nested contract versions/objective, candidate capability, package/candidate/template/source revision relationship, source event count/duration, and re-projects `reconstruction.json` from the system-maintained template events to detect mixed or tampered package files. Real CLI/Review import additionally regenerates `source-context.json` and the strict `candidate-template.json` from the current accepted Source Revision and requires exact equality, so external tools may author `candidate.json` but cannot silently rewrite the system source overview/baseline. Every artifact listed in `manifest.json` is path-confined and stream-hashed with SHA-256 before its evidence provenance is retained. Import then runs normal source-aware strict candidate normalization and coverage validation against the accepted Source Revision. The verified objective and visual/mechanical/source-alignment evidence status are retained with the immutable Candidate and remain attached to local Candidate Draft descendants. An explicit compatibility adapter continues to accept valid v3 packages (`contract.json` / `capabilities.json` / `authoring-policy.json`, source-context v2 and action-context v2); new exports never recreate that layout. A standalone `candidate.json` is still supported but is explicitly recorded as lacking package provenance. Import returns a candidate UUID and normalized digest without replacing the accepted macro. A stale source revision, unsupported field, invalid input/geometry/deadline, missing coverage, swapped/tampered package metadata, evidence hash mismatch, or disallowed restored readable value is rejected.

Open **Refine** for the current library macro (or its reconstruction menu action). Review and test the candidate through the app. **Test once** executes one iteration without chained macros; acceptance retains the original repetition/chaining settings. Receipts bind that policy and the exact Candidate content. A successful test is shown explicitly and that exact version can be accepted directly. If the Candidate needs adjustment, choose **Edit candidate** / **Edit tested version** to open a separate Candidate Draft in Macro Editor. Returning without changes preserves the same Candidate and its existing test eligibility; saving changes creates a new immutable Candidate and requires a fresh test. Editor previews are adjustment tools and do not create acceptance receipts. Playback completion, observable checks and user acceptance are separate decisions. This command family exposes no playback, success-receipt, acceptance, scheduling or restore command. Restoring the macro in the app does not undo external application actions.

`--json` uses the existing `sparkle.cli.result.v1` envelope; failures exit nonzero. Default output is a short text summary. `MacroReconstructionCLITests` supplies parser, literal candidate-ID, export/import and acceptance-gate fixtures; execution results remain in the central verification ledger.
